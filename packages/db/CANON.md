# Revenue Audit Canon (Source-of-Truth Rules)

These rules are absolute. Every surface must obey them. When a rule and a surface disagree, the surface is wrong.

The authoritative rule text lives here, next to `packages/db/src/lib/revenue-metrics.ts` (the canonical library implementing these rules). The revenue-calc unit tests at `apps/api-nest/src/modules/analytics/revenue-calc.spec.ts` enforce the math, and `scripts/canonical-audit.sh` (R1-R11 grep) guards against regressions.

## Money convention rules

**U1: Storage unit is dollars, not cents.** Every monetary column in `packages/db/prisma/schema.prisma` is a `Decimal(N,M)` storing dollar values: a $249 invoice stores as `249.00`, not `24900`. There is no integer-cents column anywhere in the schema. We trust this because Prisma's `Decimal` is fixed-precision arbitrary-precision arithmetic (backed by `decimal.js`), not IEEE-754 float: `2.49 + 7.51` is exactly `10.00`, never `10.000000000001`. The float-rounding bugs that justify integer-cents storage in JS-only systems do not apply because no money math runs in `number`/`float` space. It runs in `Decimal` end-to-end and only converts to `number` at the presentation leaf after summation (see R4).

**U2: Boundary conversions are the only legal `* 100` / `/ 100`.** Stripe speaks minor units (cents) on its API. The adapters in `apps/api-nest/src/modules/payment-providers/adapters/` divide by 100 once when reading from a provider and multiply by 100 once when writing. These are the ONLY places in `apps/` or `packages/` where a `* 100` / `/ 100` is permitted to convert a money unit. Inside the application, money is dollars from then on. Any other `* 100` / `/ 100` is either percent math (growth rates, ROI, chart pixel geometry: fine) or a bug (treating a Decimal-dollar value as if it were integer cents: not fine). There is no third option.

**U3: Monetary field and event-key names use `*_dollars` or a bare name; never `*_cents` unless it really is cents.** This applies to schema columns, DTO properties, JSON response keys, and **telemetry keys** (Sentry breadcrumbs, structured log fields, all of it). Bare names like `amount`, `totalAmount`, `unitPrice` are fine and inherit the project default of dollars. Suffixed `*_dollars` is fine when explicitness helps. The suffix `*_cents` is reserved for the U2 adapter layer and is a bug anywhere else: a future engineer reading `amount_cents: 249` in a Sentry trace will diagnose a $2.49 problem that doesn't exist while a real $249 problem goes unnoticed.

## Cost rules

**C1: Cost source.** Cost = `SUM(signal_events.usageCost)` filtered by `organizationId` and `usageDate BETWEEN window.start AND window.end`. Never derive cost from `raw_ingest_events`, `invoice_line_items`, or live model-pricing lookups at read time. `usageCost IS NULL` contributes 0 to cost but the event still counts in event-counts and must surface a "needs attention" indicator. Never silently zero. The same doctrine reaches the AI Accounting journal preview: null-cost events surface as an honest `$0` row under their default GL bucket (an expected zero, not an error) and the journal still balances.

**C1a: Matter-scoped cost.** Per-matter / Unassigned cost buckets order from exactly two canonical functions in `@marginfront/db`: `getMatterCostRollups` (the ONE SQL aggregator: `matterId: null` is the Unassigned bucket, every requested bucket returns zero-filled) and `rollupEventCosts` in `canon-math.ts` (the ONE in-memory fold, for the audit/export builders that already hold per-event rows; the dashboard `src/**` side uses the byte-faithful port in `apps/dashboard/src/lib/canon-format.ts`, pinned by `canon-format-rollup-parity.test.ts`, the same sanctioned pattern as `safeMarginPercent`, because `src/**` may not value-import `@marginfront/db`). Both carry C1's full contract: null cost adds 0, still counts, and surfaces as `eventsMissingCost`. A `signal_events` aggregate/groupBy on `usageCost` or a hand-rolled `+= usageCost ?? 0` in matter code is a violation **in the dashboard actions as much as in api-nest**. The audit script (R2/R9) only scans `apps/api-nest/src/modules`, so on the dashboard side this rule text and review grep are the enforcement. Deliberately NOT a `getCostBreakdown` dimension: the breakdown surface is reachable by any non-ingest key, while matter buckets belong to the role-gated law surface.

**C2: Cost window field.** Uses `signal_events.usageDate`, not `createdAt`. No exceptions.

## Revenue rules

The dashboard reports four distinct $-amounts for the same "revenue" concept, each with its own lens and its own margin. They MUST NOT be conflated.

| Label                 | What it measures                                                                                                                                                                                                       | Primary canon rule | Library function               |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------ | ------------------------------ |
| **Agent-Earned**      | Pure activity: events × pricing-strategy rate. No fees, no proration. A cancelled subscription's history still earns in any window it overlaps: `cancelSubscription` sets only `status='canceled'`, `endDate` stays null, and neither `getRevenueMetrics` nor `getAgentEarned` filters by status. The contract-book MRR rules below do filter to active and pending subscriptions, deliberately. "What the agent produced in the window."                                                                                                         | R1                 | `getAgentEarned()`             |
| **Revenue (formula)** | Full formula: Agent-Earned + prorated recurring fees + prorated seat fees + onetime fees when sub.startDate ∈ window. "What the customer owes us for this window."                                                     | R1 + R2            | `getRevenueMetrics()`          |
| **Billed**            | Materialized invoice totals: `SUM(invoices.totalAmount) WHERE status IN ('issued','overdue') AND invoiceDate ∈ window`. "What we sent invoices for, unpaid."                                                           | I2 + I3            | `getInvoiceTotals().billed`    |
| **Collected**         | `SUM(invoice_payments.amount − refunded_amount) WHERE payment.status = 'succeeded' AND paymentDate ∈ window`. "Cash that actually landed in the window." Cash-basis: keyed to the payment date, not the invoice date. | I2 + I3            | `getInvoiceTotals().collected` |

Each label has its own margin: `{Label} − Cost`.

**R1: Revenue from usage strategies (Agent-Earned).** For each subscription **regardless of status**, for each pricing strategy with `chargeType = 'usage'`: compute `quantity = SUM(signal_events.quantity)` for that strategy's `signalId` within the window; route through `pricingModel`: `flat` → `quantity × strategy.rate`, `graduated` → tier brackets (tier.upper is INCLUSIVE; lower is display-only), `volume` → single-rate-by-tier. Apply `Math.max(quantity, strategy.minimumCommitment)`. **This, and only this, is Agent-Earned.** No fees, no proration. A cancelled subscription's history still earns in any window it overlaps: `cancelSubscription` sets only `status='canceled'`, `endDate` stays null, and neither `getRevenueMetrics` nor `getAgentEarned` filters by status. The contract-book MRR rules below do filter to active and pending subscriptions, deliberately.

**R1a: Tier interval convention.** Tier `upper` is inclusive; `lower` is display-only and does NOT affect math. A tier with `upper:20` covers units 1 through 20 inclusive (20 billable units). Unit 21 is the first unit of the next tier. Unit tests F13 + F14 in `apps/api-nest/src/modules/analytics/revenue-calc.spec.ts` lock this in.

**R1b: Earned prices bucket-aggregated quantities, never per event.** Quantities are summed per `(subscription, signal)` across the window FIRST, then routed once through the pricing model (R1). Pricing event-by-event silently breaks every non-flat semantic: each event re-enters tier 1 of a graduated schedule (a $200 bucket reads $300), a minimum commitment never binds against any single event (a $100 floor reads $20), and status-filtered per-event strategy maps drop cancelled-subscription history ($100 of earned history reads $0). Earned totals and per-entity breakdowns (the Money breakdown dimensions, the XLSX export, Build's per-agent rows) derive from `getAgentEarned()` buckets; a parity test locks the dashboard paths to the export. Flat-rate fixtures cannot detect a violation of this rule. Regression fixtures MUST include a tier-crossing, a minimum-commitment floor, and a cancelled subscription.

**R1c: Credit pools draw in CREDITS, not units.** A `credit_pool` strategy may carry `pricing_strategies.creditRates`, a `{signalId: creditsPerUnit}` map naming which metrics burn the pool. Membership is `{strategy.signalId} ∪ keys(creditRates)`; a member with no key burns at rate 1; a signal in neither set never touches the pool. `creditRates` NULL or `{}` is a single-metric pool. Every reader multiplies the SAME way: `creditsDrawn = quantity × memberRate(strategy, signalId)`. The ledger draws it (`credit-ledger.ts` `consumeUnits`), the invoice bills the pool off the summed rated quantity of ALL members and a member signal produces NO standalone line, and the alert evaluator needs no math of its own because it reads grants that already hold rated draws. `memberRate` in `packages/db/src/lib/credit-ledger.ts` is the ONE membership-and-rate answer; a second copy of that `?? 1` is a canon violation. Rates must be finite and above zero (free means "leave the metric out", never rate 0), every key must be a live org signal, and no member signal may also carry a live `chargeType='usage'` strategy on the same plan OTHER THAN the pool strategy itself: that would burn the pool AND bill per unit, charging twice for one unit of work. The pool row is exempt by construction (`row !== pool` in `validateCreditRatesReferences`): a pool IS a live usage strategy on its own signal, so counting it would make every pool that names its own burn rate unsavable. Both write funnels enforce it with the same message (`validateCreditRatesReferences`). Per R4 there is no app-side rounding: full precision through the draw, 6dp at the `credit_ledger_entries.rateApplied` column, presented once. `rateApplied` is audit-only (NULL means rate 1) and never re-enters the math. A rate edit is not retroactive to closed periods and not deferred either: draws use the rate in force when the event arrived, and the invoice applies the live rate at close, so an edit lands on the period that is currently running.

**R2: Revenue from subscription-level fees.** `chargeType='recurring'` contributes `strategy.rate × (cycles_overlapping_window / cycle_length_in_days)` prorated to the window; for a 30-day rolling window over a monthly cycle, contribution = `rate × 1.0`. `chargeType='seat_based'` uses `max(seatsCount, minimumCommitment)` through the `pricingModel` router, also window-prorated. `chargeType='onetime'` contributes `rate` only if `subscription.startDate ∈ window`, else 0. These fees are part of **Revenue (formula)** and flow into **Billed** when invoiced. They do NOT contribute to **Agent-Earned**. Two proration lenses exist by design and must not be conflated: the window Revenue tile prorates fees over a **fixed 30-day denominator** against the clamped window (`revenue-calc.ts`: run-time-dependent, so the tile is not hand-checkable mid-cycle), while the invoice generator prorates over the **actual calendar cycle length** (`invoice-calculator.service.ts`: a full cycle is exactly 1.0). They agree at full-cycle boundaries; the invoice is the billing truth.

**R3: Canonical tier math lives in ONE file.** `packages/db/src/lib/revenue-calc.ts` exports `calcFlat`, `calcGraduated`, `calcGraduatedWithBreakdown`, `calcVolume`, `calcVolumeWithBreakdown`, `calcCreditPool`, `calcCreditPoolWithBreakdown`, `calcRouted`. All pricing math across the monorepo imports from here via `@marginfront/db`. For `flat` with empty `tiers`, use `strategy.rate`; with populated `tiers`, use `tiers[0].rate`; if both exist they must match or `calcFlat` logs a warning.

**R4: Rounding.** Display rounds to 2 decimal places exactly once, at the presentation layer (per U1, the underlying unit is dollars). Intermediate sums keep full `Decimal` precision. No `Math.round(x * 100) / 100` on values that will be summed again. The canonical fn returns full-precision Numbers; tile/table formatters round.

## Margin rule

**M1: Margin.** Applies to every one of the four $-labels: `{Label}Margin = {Label} − Cost`. `{Label}MarginPercent = ({Label} − Cost) / {Label} × 100` only when `{Label} > 0`, else `null` rendered as "—" (never "0%", never "NaN%", never "Infinity%"). Agent-Earned margin is the leading indicator: it tells you if activity is profitable even before invoices settle. Org-level caveat: the Revenue-Margin% tile derives revenue AND cost from the subscription-attributed lens (`getRevenueMetrics`), while the org Cost tile counts every event including unattributed ones. The two can legitimately disagree, so an org-level Margin% is not a hand-checkable oracle; margins are verified at entity level.

**M2: Scalar derivations return null when undefined.** `growthPercent(current, previous)` → null when `previous <= 0` (growth from a zero base is "new", not "+∞%" or a fake "+100%"); `shareOfTotal(part, total)` → null when `total === 0`; `avgPer(sum, count)` and `costPerTask(cost, taskCount)` → null when the count is 0. Same family as M1: null renders "—"; a caller may coalesce deliberately, never silently. Canonical implementations: `packages/db/src/lib/canon-math.ts`. Hand-rolled copies of these shapes outside the canonical library are banned (ESLint). The API's `/v1/analytics/*` responses carry the honest null too: field names and types stay stable, and no `?? 0` fills the gap.

## Invoice rules

**I1: Invoices reconcile by construction.** For every non-draft invoice: `sum(invoice_line_items.amount)` for its cycle ≡ `getRevenueMetrics(orgId, {start: billingPeriodStart, end: billingPeriodEnd}, {subscriptionId: invoice.subscriptionId}).revenue`. The runtime invoice generator builds line items by calling the same function the dashboard calls.

**I2: Invoice status canon.** Statuses in play: `{draft, issued, paid, overdue, void}`, plus `refunded`, which the refund finalizer sets when a whole invoice is refunded. The enum also lists `pending`; no rule counts it. `Billed = SUM(totalAmount) WHERE status IN ('issued','overdue')` (accrual). `Collected` is cash-basis: `SUM(invoice_payments.amount − refunded_amount) WHERE payment.status = 'succeeded' AND paymentDate ∈ window`, not a sum of paid-invoice totals. `Outstanding = SUM(totalAmount) WHERE status IN ('issued','overdue')` measured at CURRENT STATE with no date window (open accounts-receivable right now); it is **not** `billed − collected`, because billed (accrual) and collected (cash) are different bases and the subtraction could go negative. `Draft` is never Billed. `Void` is never counted anywhere.

**I3: Invoice date fields.** Billed (accrual) filters on `invoiceDate BETWEEN window.start AND window.end`, not `createdAt`, not `dueDate`, not "cycle overlaps window." Collected (cash) filters on `invoice_payments.paymentDate BETWEEN window.start AND window.end`, the date the cash actually landed. A `status='paid'` invoice with **no** payment row has no cash date, so it falls back to invoiceDate windowing and is logged (so the data gap is loud, not silent).

**I4: Invoice aging buckets.** Open invoices (status `issued`/`overdue`) bucket by days overdue relative to now, on UTC calendar days (canon W1): current (≤ 0 days or no due date), 1-30, 31-60, 61-90, 91+, with inclusive edges, every invoice in exactly one bucket. Canonical implementation: `invoiceAgingBuckets` in `canon-math.ts`. This is the single definition.

## MRR rules

**MRR1: MRR definition.** Contracted monthly recurring revenue, today (industry-standard SaaS MRR). For every `active` or `pending` subscription: `recurring` strategies contribute `strategy.rate` (÷ 12 on a yearly billing cycle); `seat_based` strategies contribute `max(seatsCount, minimumCommitment) × strategy.rate`, monthly-normalized the same way; `usage` and `onetime` strategies are excluded (usage run-rate belongs to MRR2, usage contract floors to MRR3). `ARR = MRR × 12`. Forward-looking: "what does the current subscription book commit to per month?" Canonical implementation: `getMrr` in `packages/db/src/lib/revenue-metrics.ts`.

**MRR2: Run-Rate MRR.** Contract-based commitments plus last-30-days usage activity, monthly-normalized. For each active + pending subscription: `recurring` strategies contribute `strategy.rate / 12` when the sub is on a yearly cycle, else `strategy.rate`; `seat_based` strategies contribute `max(seatsCount, minimumCommitment) × strategy.rate` with the same monthly normalization; `usage` strategies route actual last-30-days events through `calcRouted(strategy, quantity)` (min-commitment applied to the 30-day quantity before the calc); `onetime` strategies are excluded. `Run-Rate ARR = Run-Rate MRR × 12`. Forward-looking: "what would we bill per month if the last 30 days kept going?" Canonical implementation: `getRunRateMrr`.

**MRR3: Committed MRR (CMRR).** Pure contractual floor: same shape as MRR2 but `usage` strategies contribute `calcRouted(strategy, minimumCommitment)` (or 0 when the strategy has no minimum) instead of actual 30-day usage. Independent of activity. Useful for forecasting; not surfaced on the dashboard by default. Canonical implementation: `getCommittedMrr`.

## Event ingestion validation rules

These rules govern what the ingestion endpoint accepts. They run before cost is computed, and determine whether an event lands as `PROCESSED`, `MISSING_VOLUME_DATA`, or `NEEDS_COST_BACKFILL`. All downstream cost, revenue, and invoice math assumes these rules held on write.

**V1: LLM events require tokens.** Events whose resolved `service_pricing.costUnit` is `'1M tokens'` MUST carry both `inputTokens` AND `outputTokens` on the incoming record. Missing either (null or undefined) stores the event as `MISSING_VOLUME_DATA` with `usageCost = null`. Explicit `0` is valid and stores as `PROCESSED` with `usageCost = 0`. Source: `recordUsage` in `apps/api-nest/src/modules/sdk/sdk.service.ts`.

**V2: Non-LLM events require quantity.** Events whose `costUnit` is anything other than `'1M tokens'` MUST carry `quantity` on the incoming record. Missing stores as `MISSING_VOLUME_DATA`. Explicit `0` is valid and stores as `PROCESSED` with `usageCost = 0`. Source: `recordUsage` in `sdk.service.ts`.

**V3: Quantity is not part of LLM cost math.** For LLM rows, `usageCost = inputTokens × (inputCost / 1M) + outputTokens × (outputCost / 1M) + cacheReadTokens × (cacheReadCost / 1M) + cacheWriteTokens × (cacheWriteCost / 1M)`. The two cache terms price prompt-cache hits (`cacheReadTokens` at the cheaper cache-read rate, ~0.1× input on Anthropic) and prompt-cache creation (`cacheWriteTokens` at the cache-write rate) separately from fresh input. Folding them into the input rate over- or under-counts cache-heavy traffic by 5 to 10×. A missing cache token count contributes exactly $0, so rows/events without cache compute identically to the two-term formula without cache terms. A missing cache _rate_ also contributes $0 in `calculateEventCost` itself (the math layer treats a null rate as 0), EXCEPT when the event actually reports cache tokens: that case (enforcing C1) is intercepted at ingest (`sdk.service.ts`) and the event is stored with `usageCost: null` and flagged `NEEDS_COST_BACKFILL` rather than silently priced low, so the missing rate surfaces in the needs-attention queue instead of under-billing in silence. A genuine $0.00 cache rate is NOT a missing rate: `toLookupResult` preserves it as `0` (via `!= null`, not a truthy check), so a legitimately-free-cache row prices to $0 and is never flagged. Cache cost folds into the child `usageCost`, so the parent SUM rollup (C1) is unchanged, with no new top-level column. `cacheWriteCost` on Anthropic LLM rows holds the 1-HOUR-TTL ceiling (2× `inputCost`, written by the sync script's override in `scripts/sync-service-pricing.ts`) so an unknown TTL can never under-bill; an event stamped `metadata.cacheWriteTtl = "5m"` (sent by the code-cost-clarity meter) is priced at 1.25× `inputCost` via `applyCacheWriteTtl` in `model-pricing.ts`, and EVERY re-pricer (ingest, dashboard backfill, future recomputes) must route the event's stored hint through that helper. Skipping it re-prices a 5m event at the ceiling and breaks reproducibility. A missing/unknown hint keeps the ceiling rate. Quantity on an LLM event is metadata only, used downstream for signal-based revenue attribution (R1 → `calcRouted` on the subscription's pricing strategy), never for cost. For non-LLM rows, cost IS quantity-driven (`quantity × inputCost` for flat per-unit, `quantity × inputCost / 1000` for per-1K-unit `"1K …"`, and `quantity × inputCost / 1_000_000` for per-1M-unit `"1M …"` non-token rows such as Pinecone read units, Cloud Run requests and TTS characters) and cache terms never apply. Source: the LLM branch of `calculateEventCost` in `packages/db/src/lib/model-pricing.ts`.

**V4: Quantity defaults to 1 for storage, only after V1/V2 fire.** Both the TypeScript SDK (`packages/sdk/src/resources/usage.ts`) and the NestJS ingestion API (`recordUsage` in `sdk.service.ts`) apply `record.quantity ?? 1` when writing to `raw_ingest_events.payload`, so the stored payload always carries a numeric quantity. The default runs AFTER V1/V2 have evaluated the incoming record, so raw-HTTP callers who send no quantity still hit MISSING_VOLUME_DATA. Storage convenience, not validation bypass.

## Window rule

**W1: Window uniformity.** "Last 30 days" = `[now − 30d, now]` inclusive, computed ONCE per request in UTC, threaded to every calculation. No surface re-derives a window mid-render.

## Attribution rule

**A1: Attribution.** Customer → Subscription → (Plan, Agent). Events attribute via `signal_events.subscriptionId` first; if null, fall back via `(customerId, agentId, signalId)` join against active subscriptions valid at the event's `usageDate`. Aggregations "by agent" / "by customer" / "by plan" use the resolved subscription path.

## Label rule

**L1: Labels & tooltips.** Every `$`-valued surface on the dashboard displays a label tied to exactly one of the four canon terms (Agent-Earned / Revenue / Billed / Collected) and has an `InfoTooltip` whose body cites the canon rule it enforces.

Dashboard labels may use approachable shorthand provided the tooltip cites the canon rule and the precise formula. Current shorthand mappings:

| Dashboard label                          | Canon term               | Applies to                                                               |
| ---------------------------------------- | ------------------------ | ------------------------------------------------------------------------ |
| "Earned"                                 | Agent-Earned             | Revenue Funnel stage, per-agent activity tiles                           |
| "Total Margin"                           | Revenue (formula) Margin | KPI tile on Full + Revenue modes + customer detail + subscription detail |
| "Agent-Earned Margin" or "Earned Margin" | Agent-Earned Margin      | Per-agent cards where the margin is activity-scoped                      |
| "Billed Margin"                          | Billed Margin            | Surfaces scoped to invoice totals                                        |
| "Collected Margin"                       | Collected Margin         | Surfaces scoped to paid invoices                                         |

The canon term remains the source of truth in this file, the docs and the tests; the shorthand is dashboard-layer presentation. A bare "Margin" or "Gross Margin" label is a violation: every margin surface must name its variant (shorthand or full).
